# KLEE-Based UAF Detection Demo (STASE-Style)

## Overview

This demo illustrates how to use **KLEE symbolic execution** to **confirm a Use-After-Free (UAF)** vulnerability in a non-trivial C codebase (`metalogin.c`) using a **STASE-style workflow**:

> **Static Analysis → Targeted Driver → Environment Stubs → Symbolic Confirmation**

The key lesson is that **symbolic execution alone does not automatically find bugs**. To make KLEE effective, we must:
- isolate the vulnerable behavior,
- control the execution environment,
- and explicitly encode what “failure” means.

This repository shows how to do that in a minimal, reproducible way suitable for teaching.

---

## Vulnerability Summary

### Type
**Use-After-Free (UAF) / stale pointer**

### Bug Pattern
1. An `avatar` object is dynamically allocated.
2. A global pointer (`g_session.current_avatar`) aliases that object.
3. The object is freed in `clear_avatar()`.
4. The global pointer is **not reliably invalidated**.
5. Later code still uses the pointer.

This is a classic **object lifetime violation**.

---

## Why KLEE Does Not Flag the Bug Automatically

KLEE reports errors **only when it observes an invalid operation**.

In this program:
- The freed pointer may remain non-NULL.
- The pointer may be passed around without dereference.
- The dereference may occur inside stubbed or library code.
- Some paths may never reach the dereference.

Therefore, the UAF exists *semantically*, but KLEE needs to be told **where and how to check**.

## High-Level Procedure

### Step 1: Identify the Vulnerable Path (Manual)

From code inspection or static analysis, we identify the minimal path:

```
init_system()
  → set_avatar(username, access_code)
  → clear_avatar()
  → render_hex()
```

This path:
- creates the object,
- frees it,
- and then uses it.

In a full STASE system, this information would come from static analysis
(CodeQL, rule-based analysis, or vulnerability signatures).

---

### Step 2: Driver Generation (Manual)

File: `driver_uaf_demo.c`

The driver:
- replaces the program’s original `main()`,
- avoids interactive menu logic,
- executes only the vulnerable path,
- inserts a **memory-safety check**.

Key line:

```c
klee_check_memory_access(g_session.current_avatar, sizeof(avatar));
```

This explicitly asks:
> “Is this pointer still valid memory?”

If the pointer is stale, KLEE reports a **memory error**.

> **Note:** The error is reported in the driver because the check is placed there.
> This is intentional and standard in STASE-style confirmation.

---

### Step 3: Symbolic Input Modeling (Manual, Minimal)

We make only the necessary inputs symbolic:

```c
klee_make_symbolic(username, sizeof(username), "username");
klee_make_symbolic(access_code, sizeof(access_code), "access_code");
```

Constraints are intentionally minimal:
- Force null termination concretely.
- Require a non-empty username.

```c
klee_assume(username[0] != 0);
```

We avoid over-constraining, which prevents:
- `invalid klee_assume` errors,
- path explosion,
- contradictory constraints.

---

### Step 4: Stub Generation (Automated)

File: `stubs_demo.c`  
Generated by: `stub.sh`

#### Why Stubs Are Needed
Real programs depend on:
- libc (`strlen`, `strcmp`, `strdup`, …)
- I/O (`fgets`, `scanf`, `stdin`)
- math (`sin`, `cos`)
- UI helpers (`print_card`)

KLEE cannot reason about these directly.

#### What the Stubs Do
- Provide small, deterministic models for libc functions.
- Disable interactive input paths.
- Prevent calls to external functions.
- Keep symbolic execution focused on relevant logic.

This step is **environment generation**, and it is essential.

---

### Step 5: Environment Normalization (Automated)

Script: `stub.sh`

`stub.sh` performs:
- Guarding the program’s original `main()` with:
  ```c
  #ifndef KLEE_DRIVER_BUILD
  ```
- Ensuring the driver owns `main()`.
- Writing a correct `build.sh`.
- Writing a complete `stubs_demo.c`.
- Making the project compilable with `clang -emit-llvm`.

This step is fully automated.

---

### Step 6: Build LLVM Bitcode (Automated)

```bash
./stub.sh
./build.sh
```

Produces:
```
uaf_demo.bc
```

This bitcode includes:
- the driver,
- the target logic,
- the stubs,
- and a single entry point.

---

### Step 7: Run KLEE (Automated)

```bash
bash run.sh
```

Observed result:

```
ERROR: driver_uaf_demo.c:70: check_memory_access: memory error
generated tests = 450
```

The UAF is **successfully confirmed**.

## Automated vs Manual Components

### Automated
- Environment normalization (`stub.sh`)
- Stub generation (`stubs_demo.c`)
- Build orchestration (`build.sh`)
- Symbolic execution (`run.sh`)
- Memory error detection (KLEE)

### Manual (By Design)
- Identifying the vulnerable path
- Deciding where to place the check
- Choosing the correct assertion/check
- Writing the driver logic
- Selecting symbolic inputs

> **STASE principle:** automate mechanics, not reasoning.

---

## Why the Error Appears in the Driver

The error is reported at:

```
driver_uaf_demo.c:70
```

because that is where `klee_check_memory_access` is called.

If the check were inserted inside `render_hex()` in `metalogin.c`,
the error would be reported there instead.

In a full STASE pipeline:
- static analysis identifies the use site,
- instrumentation is applied to the target source,
- the driver only guides execution.

This demo keeps instrumentation in the driver for clarity.

## Generalizing to Other Vulnerabilities

### 1. Vulnerability Modeling (Manual)
Determine:
- What object or value is unsafe?
- What invariant is violated?
- Where is the use site?

Examples:
- OOB write → index vs buffer size
- Double free → allocator state
- Null dereference → dereference guard
- Type confusion → object layout

---

### 2. Driver Generation
- Remove UI and setup noise.
- Execute only the minimal triggering path.
- Make only relevant inputs symbolic.
- Keep constraints minimal.

---

### 3. Assertion / Check Selection
Use:
- `klee_check_memory_access` for memory safety,
- `klee_assert` for semantic properties,
- custom predicates for domain-specific bugs.

---

### 4. Stub Reuse
- Maintain a reusable stub library.
- Extend only when new symbols appear.
- Keep stubs simple and deterministic.

---

### 5. Environment Generation
- One normalization script (`stub.sh`) per project.
- Reusable across multiple drivers and bugs.
- Key to scalability for large codebases.

---

## Key Takeaways

- KLEE does not automatically “find” bugs.
- Bugs must be **modeled**, **targeted**, and **checked**.
- Drivers, stubs, and environment control are essential.
- This approach scales to kernels, firmware, and large systems.

This demo is a minimal, correct example of **STASE-style symbolic confirmation**.
